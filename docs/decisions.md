## Реестр решений:

### [2026-10-20] Инициализация проекта
- **Контекст:** Старт проекта tg-search в пространстве «Мои проекты».
- **Решение:** Выбран архетип `Engineering & Services (Код / Бэкенд / MCP / API / CLI)`, создана базовая структура каталогов и документов.
- **Обоснование:** Соответствие единому стандарту рабочего пространства Кирилла Вечкасова.
- **Последствия:** Проект готов к автономной работе ИИ-ассистентов в подразделах BB.

### [2026-10-20] Форма продукта и движок
- **Контекст:** аналог SignalDesk: поиск лидов в Telegram с ИИ-квалификацией и автопилотом.
- **Решение:** десктоп на Electron + React; Telegram через официальный TDLib 1.8.67 (`tdl` + `prebuilt-tdlib`), а не GramJS; хранилище `node:sqlite`; ИИ через OpenAI-совместимый API (OpenRouter, `anthropic/claude-haiku-5.5`).
- **Обоснование:** TDLib — актуальный слой API с `searchPublicPosts(query)` (глобальный поиск постов по слову), GramJS застрял на слое 198. `node:sqlite` не требует нативной пересборки под Electron. OpenRouter-ключ уже есть, Haiku 5.5 дешёвый для массовой квалификации.
- **Последствия:** один процесс TDLib-клиента на аккаунт в main; ID чатов и пользователей общие для всех аккаунтов.

### [2026-10-20] Отправка: полный автопилот с лимитами
- **Контекст:** владелец выбрал полный автопилот ответов, отдельные рабочие аккаунты.
- **Решение:** автопилот выключен по умолчанию; при включении отвечает только лидам со score ≥ `minScore`, соблюдает дневной лимит (10) и паузу (180 с) на аккаунт, один ответ на лида.
- **Последствия:** вся отправка идёт через единый ограничитель в конвейере, UI и автопилот не шлют в обход него.

### [2026-10-20] Параллельная разработка
- **Решение:** модули пишут воркеры Composer 2.5 (`cursor-agent`) в отдельных git worktree и ветках `feat/*`; лид-агент сливает в `main` после typecheck и тестов. Контракты (`src/shared/types.ts`, `src/main/*/types.ts`) меняет только лид.

### [2026-10-20] Автоответы: проверка перед отправкой, без повторов
- **Решение:** очередь автопилота перед отправкой заново проверяет, что ответы включены, лид в статусе `new` и ему ещё ничего не отправляли. Неудачный автоответ (закрытая личка, нет прав в чате) не повторяется до перезапуска приложения, ошибка уходит событием `job`.
- **Обоснование:** иначе ручной ответ + автоответ дают двойное сообщение, а повтор каждые 30 с бьёт по лимитам Telegram и бюджету LLM.

### [2026-10-20] Квалификация через Jev, мониторинг в реальном времени, CSV, рассыльщик
- **Контекст:** владелец прислал ТЗ из чата: несколько юзербот-аккаунтов в разных чатах, импорт чатов из CSV, слежение за новыми сообщениями, оценка через Jev 1.14 с промптом под каждую тематику, автосообщение подходящим авторам, периодическая рассылка оффера в выбранные чаты.
- **Решение:**
  - Квалификация сообщений — Jev 1.14 (TypeSafe System One) через OpenLux `https://api.openlux.ai/v1/systemone`, модель `jev-1.14.0`; у проекта поле `criteria` — промпт «что нам подходит». Без ключа Jev квалифицирует LLM. LLM остаётся для ключей, оценки чатов, черновиков и вариаций текста рассылки.
  - Новые сообщения из чатов, где состоят аккаунты, приходят через `onChatMessage` и сразу квалифицируются (кроме периодического скана).
  - `sources.importCsv`: первая колонка — ссылка или @username; вступление в чаты идёт в фоне с паузами, распределяется по аккаунтам проекта.
  - Рассылки (`broadcasts`): текст, аккаунты по кругу, чаты, интервал на чат, вариация текста LLM; все посты проходят общий лимитер аккаунта.
- **Обоснование:** проверка Jev: ~0,9 с на запрос, «явный запрос на услугу» 96%, «конкурент» 4% на тестовом сообщении. Через `api.typesafe.ai` доступна только jev-1.13, 1.14 — через OpenLux.
- **Последствия:** сообщение может прийти от нескольких аккаунтов — дедупликация по `chatId:messageId` (таблица `seen`). Вступления и рассылки — главный риск ограничений Telegram, поэтому паузы и лимиты обязательны.
