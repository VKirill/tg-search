## Реестр решений:

### [2026-10-20] Инициализация проекта
- **Контекст:** Старт проекта tg-search в пространстве «Мои проекты».
- **Решение:** Выбран архетип `Engineering & Services (Код / Бэкенд / MCP / API / CLI)`, создана базовая структура каталогов и документов.
- **Обоснование:** Соответствие единому стандарту рабочего пространства Кирилла Вечкасова.
- **Последствия:** Проект готов к автономной работе ИИ-ассистентов в подразделах BB.

### [2026-10-20] Форма продукта и движок
- **Контекст:** аналог SignalDesk: поиск лидов в Telegram с ИИ-квалификацией и автопилотом.
- **Решение:** десктоп на Electron + React; Telegram через официальный TDLib 1.8.67 (`tdl` + `prebuilt-tdlib`), а не GramJS; хранилище `node:sqlite`; ИИ через OpenAI-совместимый API (OpenRouter, `anthropic/claude-haiku-5.5`).
- **Обоснование:** TDLib — актуальный слой API с `searchPublicPosts(query)` (глобальный поиск постов по слову), GramJS застрял на слое 198. `node:sqlite` не требует нативной пересборки под Electron. OpenRouter-ключ уже есть, Haiku 5.5 дешёвый для массовой квалификации.
- **Последствия:** один процесс TDLib-клиента на аккаунт в main; ID чатов и пользователей общие для всех аккаунтов.

### [2026-10-20] Отправка: полный автопилот с лимитами
- **Контекст:** владелец выбрал полный автопилот ответов, отдельные рабочие аккаунты.
- **Решение:** автопилот выключен по умолчанию; при включении отвечает только лидам со score ≥ `minScore`, соблюдает дневной лимит (10) и паузу (180 с) на аккаунт, один ответ на лида.
- **Последствия:** вся отправка идёт через единый ограничитель в конвейере, UI и автопилот не шлют в обход него.

### [2026-10-20] Параллельная разработка
- **Решение:** модули пишут воркеры Composer 2.5 (`cursor-agent`) в отдельных git worktree и ветках `feat/*`; лид-агент сливает в `main` после typecheck и тестов. Контракты (`src/shared/types.ts`, `src/main/*/types.ts`) меняет только лид.

### [2026-10-20] Автоответы: проверка перед отправкой, без повторов
- **Решение:** очередь автопилота перед отправкой заново проверяет, что ответы включены, лид в статусе `new` и ему ещё ничего не отправляли. Неудачный автоответ (закрытая личка, нет прав в чате) не повторяется до перезапуска приложения, ошибка уходит событием `job`.
- **Обоснование:** иначе ручной ответ + автоответ дают двойное сообщение, а повтор каждые 30 с бьёт по лимитам Telegram и бюджету LLM.

### [2026-10-20] Квалификация через Jev, мониторинг в реальном времени, CSV, рассыльщик
- **Контекст:** владелец прислал ТЗ из чата: несколько юзербот-аккаунтов в разных чатах, импорт чатов из CSV, слежение за новыми сообщениями, оценка через Jev 1.14 с промптом под каждую тематику, автосообщение подходящим авторам, периодическая рассылка оффера в выбранные чаты.
- **Решение:**
  - Квалификация сообщений — Jev 1.14 (TypeSafe System One) через OpenLux `https://api.openlux.ai/v1/systemone`, модель `jev-1.14.0`; у проекта поле `criteria` — промпт «что нам подходит». Без ключа Jev квалифицирует LLM. LLM остаётся для ключей, оценки чатов, черновиков и вариаций текста рассылки.
  - Новые сообщения из чатов, где состоят аккаунты, приходят через `onChatMessage` и сразу квалифицируются (кроме периодического скана).
  - `sources.importCsv`: первая колонка — ссылка или @username; вступление в чаты идёт в фоне с паузами, распределяется по аккаунтам проекта.
  - Рассылки (`broadcasts`): текст, аккаунты по кругу, чаты, интервал на чат, вариация текста LLM; все посты проходят общий лимитер аккаунта.
- **Обоснование:** проверка Jev: ~0,9 с на запрос, «явный запрос на услугу» 96%, «конкурент» 4% на тестовом сообщении. Через `api.typesafe.ai` доступна только jev-1.13, 1.14 — через OpenLux.
- **Последствия:** сообщение может прийти от нескольких аккаунтов — дедупликация по `chatId:messageId` (таблица `seen`). Вступления и рассылки — главный риск ограничений Telegram, поэтому паузы и лимиты обязательны.

### [2026-10-20] Основной режим — прослушка всех чатов аккаунтов
- **Контекст:** владелец: аккаунт и так получает сообщения мгновенно — сканировать надо всё, что приходит, без поиска по фразам.
- **Решение:** каждое новое сообщение из любой группы, супергруппы или канала, где состоит аккаунт проекта (публичного или приватного), сразу идёт в Jev. Чат становится источником проекта с первым сообщением (`foundBy: 'member'`); источник со статусом `rejected` не слушается. Поиск по фразам остаётся кнопкой «Найти новые чаты» — для расширения списка, куда вступить.
- **Последствия:** текст приватных групп тоже уходит во внешний API Jev — исключение делается отклонением источника. Глобальный поиск постов (`searchPublicPosts`) требует Telegram Premium; без него движок отключает этот поиск для аккаунта после первой ошибки.

### [2026-10-20] Цепочки, ИИ-менеджер, передача человеку, скилл для Claude
- **Контекст:** владелец: интерфейс должен позволять создавать тематики (что искать), строить цепочки отправки и подключать любую ИИ-модель, которая общается как менеджер, доводит человека до заказа и передаёт его владельцу. Плюс скилл, чтобы настраивать всё это из Claude словами.
- **Решение:**
  - `Project.sequence` — шаги цепочки (`template` с `{name}`/`{request}` или `ai` — инструкция для ИИ), задержка в часах; следующий шаг уходит только пока лид молчит. Ответ лида останавливает цепочку.
  - `Project.manager` — ИИ-менеджер на любой OpenAI-совместимой модели (свой base URL/ключ/модель или глобальные), промпт с ролью, целью и правилами, пауза перед ответом, лимит ответов. Возвращает ответ или решение «передать человеку» (`Lead.handoff`). Песочница `manager.test` — проверить менеджера без Telegram.
  - `Settings.handoffNotifyTo` — @username владельца, которому рабочий аккаунт пишет сводку при передаче диалога; это служебное сообщение владельцу, не рассылка — лимитер к нему не применяется.
  - Сообщения ботов (`TgMessage.senderIsBot`) не квалифицируются.
  - Локальный API управления (127.0.0.1, токен в userData) + CLI `tgs` + скилл `skills/tg-search/SKILL.md` для Claude Code.

### [2026-10-20] Мини-CRM: карточка клиента, анамнез, ТЗ, голос, записи созвонов
- **Контекст:** владелец: система — мини-CRM поиска и ведения клиентов. Помощник представляется помощником Кирилла, собирает анамнез и формирует ТЗ, по которому Кирилл назовёт цену. Голосовые (в т.ч. в будущем клоном голоса), созвоны с автозаписью и транскрибацией в ТЗ. Раскладка: меню слева → чаты → переписка → CRM-карточка справа.
- **Решение:**
  - `ClientCard` на каждого лида: этап воронки (`DealStage`), саммари «на чём остановились», структурированный `Anamnesis` (задача, цель, аудитория, функционал, интеграции, стек, сроки, бюджет, примеры, контакты, открытые вопросы), `completeness`, Markdown-ТЗ, заметки. Обновляется LLM по всей переписке, включая расшифровки голосовых и созвонов.
  - ИИ-менеджер получает анамнез и открытые вопросы и задаёт их по одному; передаёт диалог, когда анамнез собран или клиент просит цену/созвон/человека.
  - Персона (уточнено владельцем): на вопросы «ты бот?», «кто ты?» отвечает только «я помощник {ownerName}, собираю заявку» и возвращается к задаче. Граница: не называет себя живым человеком и не говорит «я не бот» — прямая ложь о человеческой природе подрывает доверие клиента к владельцу и рискованна для аккаунта.
  - Голос: входящие голосовые скачиваются и расшифровываются (OpenAI-совместимый `/audio/transcriptions`, по умолчанию `gpt-4o-transcribe`); исходящие — TTS (`/audio/speech`, `gpt-4o-mini-tts`, голос `nova`) → OGG/Opus через ffmpeg → голосовое Telegram. Клон голоса — следующий шаг (MiniMax/ElevenLabs), пока общий голос.
  - Созвоны: звонки из приложения ИИ-агентом **отключены** — TDLib даёт только сигнализацию звонков, медиа-слой (tgcalls/WebRTC) — отдельный крупный модуль. Вместо этого запись созвона, который владелец ведёт на этом Mac (микрофон + системный звук), → расшифровка → обновление карточки и ТЗ.

### [2026-10-21] Раздел «Чаты»: ручной клиент Telegram
- **Контекст:** владелец хочет работать с чатами вручную, как в Telegram Desktop: видеть подписки, отписываться, искать и вступать в новые чаты.
- **Решение:** раздел «Чаты» — список чатов аккаунта (`getChats`), история страницами по 50 с подгрузкой ранних, ответы, голосовые, поиск (свои чаты + публичные), вступление по id/@username/ссылке/приглашению, выход; справа — «Прослушка» по тематикам (статус источника). Ручные сообщения из этого раздела **не проходят лимитер** — это переписка владельца, а не рассылка; лимитер остаётся на автопилоте, цепочках, менеджере и рассылках. Открытие чата не отмечает сообщения прочитанными.
- **Безопасность:** схема `tgmedia://` отдаёт только файлы внутри userData (раньше — любой путь на диске).

### [2026-10-21] Статистика и карта спроса по категориям
- **Контекст:** владелец хочет видеть расходы (Jev и др.) по дням/неделе/месяцу, объём проанализированного, долю болтовни — и понимать, какие ниши спроса растут (IT, реклама, фото/видео, домашние задания, карточки маркетплейсов…), чтобы под них строить новых исполнителей.
- **Решение:**
  - Каталог категорий спроса (редактируемый, со стартовым набором). Каждое новое сообщение классифицируется **один раз глобально** одним запросом Jev: Choice по категориям (+ «нет подходящей») и Noul «это запрос на услугу/помощь». Результат — таблица `classified`.
  - Сообщения с вероятностью запроса ниже порога (`requestThreshold`, 0.2) не идут в квалификацию тематик — экономия на болтовне. Если классификатор недоступен, сообщения проходят без фильтра (fail-open), лиды не теряются.
  - Учёт расходов в `usage`: LLM через OpenRouter — точная стоимость из ответа (`usage.include`), Jev — по цене OpenLux (~$0.042 за 1 млн входных токенов, выход бесплатен; множитель группы `jev-1` не опубликован — оценка), речь — по минутам и ценам из настроек.
  - Раздел «Статистика»: плитки, сообщения по дням (запросы/болтовня), расходы по дням, спрос по категориям с примерами, расходы по моделям. Цвета серий проверены валидатором dataviz на тёмной поверхности.

### [2026-10-21] Исполнители: ИИ-менеджер сам продаёт, берёт оплату и выполняет простые задания
- **Контекст:** владелец хочет, чтобы система сама доводила простые заказы до результата (домашка по фото, карточки маркетплейсов, нейрофото, тексты и контент-планы), выставляла счёт по рыночной цене и подключала владельца только когда нужно. Клиенты брифа не дают — только хотелки, ссылки на конкурентов, аккаунты; агент думает наперёд и предлагает превью, чтобы поднять чек. По каждому клиенту — документальная «подноготная» в файлах.
- **Решение:**
  - `Service` — каталог услуг с вилкой цен, инструкцией-скиллом (что спросить, как оценить, планка качества, формат сдачи), моделью исполнителя, превью и числом правок. Четыре стартовые услуги, вилки по рынку (Kwork, студенческие биржи, 2026-10): домашка 300–1500 ₽, карточка 500–3000 ₽, нейрофото 500–2500 ₽, тексты/контент-план 300–3000 ₽. Агент называет цену только внутри вилки.
  - `Order` — заказ по лиду: сбор хотелок и допущений → цена → оплата → выполнение → сдача → правки → готово; ошибки и нестандарт → передача владельцу.
  - Оплата — ЮKassa (пока тестовый магазин, потом рабочий): ссылка на оплату, проверка статуса, после `succeeded` — запуск исполнителя. Ручное подтверждение оплаты — кнопка в карточке.
  - Подноготная клиента — папка `userData/clients/<lead>/`: профиль, история общения, заказы с файлами и результатами; ведёт вспомогательная модель (9router `ag/gemini-3.8-flash`, нужен `stream: false`).
  - Изображения — fal.ai. **Фото клиента (в том числе аватар из Telegram) используется для превью только после его явного согласия** — агент сначала спрашивает.
  - Движок получил отправку фото и документов, распознавание входящих фото и документов, аватар пользователя.

### [2026-10-21] Долгосрочный агент: память клиента, оператор на инструментах, подписки
- **Контекст:** владелец: система должна годами вести клиентов как самостоятельный менеджер и личный ассистент — помнить всё и переиспользовать материалы через месяц, выполнять любые поручения (в том числе поиск и исследования), продавать заказы и ежемесячную подписку, проверять оплату и сообщать о ней. Память клиента — локальная, мультимодальная.
- **Решение:** см. [architecture-agent.md](architecture-agent.md). Состояние в базе, модель без состояния (никаких долгоживущих CLI-сессий): `Client` объединяет лиды одного человека; память — факты, эпизоды (сжатие переписки), файлы с подписями; контекст хода собирается с бюджетом токенов. Оператор — цикл вызовов инструментов (по умолчанию DeepSeek V4.1 Flash `deepseek-flash`, 1 млн контекста, видит картинки), правила зашиты в инструменты. Поиск по памяти — EmbeddingGemma 2 локально (transformers.js, ONNX q4) + FTS5, гибрид. Подписки с квотой поручений, журнал платежей ЮKassa, напоминания о продлении. Новый исполнитель `assistant` — поиск в сети (Tavily), исследование, поручения.
- **Обоснование:** подписки на чат-модели (Claude Code, GLM через opencode) для автоматического обслуживания клиентов могут нарушать их условия; API-ключи — надёжнее. Гарантии в коде, а не в промпте, переживают смену модели.

### [2026-10-21] Оператор на GLM 5.3 Flash с переключателем; умения в формате SKILL.md
- **Решение:** по выбору владельца оператор по умолчанию — GLM 5.3 Flash (Z.ai, OpenAI-совместимый endpoint `https://api.z.ai/api/coding/paas/v4`), переключатель в настройках на DeepSeek V4.1 Flash или свой адрес, ключ у каждого провайдера свой (`operatorProvider`, `glmApiKey`, `deepseekApiKey`, разрешение — `src/main/agent/provider.ts`). Сессии opencode не используем: GLM вызывается напрямую тем же ключом, а «сессия» — это память клиента в базе. Умения агента — `SKILL.md` (совместим с opencode/Claude Code), загрузка инструментом `load_skill`, подсказка Jev, черновики новых умений по повторяющимся задачам — на утверждение владельцу.
- **Оговорка:** ключ из Z.ai Coding Plan рассчитан на инструменты разработки; если условия плана запрещают обслуживание клиентов ботом — переключить на платный API Z.ai (тот же код, другой ключ) или DeepSeek.

### [2026-10-21] Тематики лидов — категория спроса на лиде, а не отдельные поиски
- **Контекст:** владелец хочет сразу видеть лидов разложенными по направлениям (Яндекс Директ, сайты, дизайн, карточки…), а фильтр «Все тематики» показывал единственный поиск «Клиенты на разработку».
- **Решение:** один широкий поиск «Клиенты» с правилом Jev на любые наши услуги; у лида — `categoryId` из карты спроса (тот же проход Jev, что уже размечает каждое сообщение, без лишних вызовов). Старые лиды размечаются один раз при запуске. Во «Входящих» и «Лидах» фильтр по категориям со счётчиками, на карточке — метка; выбор поиска появляется, только если поисков больше одного. Категории раздроблены: сайты, Директ и контекст, Telegram-боты и автоматизация, таргет и SMM, SEO, дизайн, фото и видео, карточки, тексты, учёба.
- **Почему не отдельные поиски:** каждый поиск заново прогоняет каждое сообщение через Jev и требует своих источников — дороже в N раз при той же информации.

### [2026-10-21] «Electron 20 ГБ» в окне принудительного завершения — чужие процессы
- **Контекст:** окно «Принудительное завершение» показывало Electron на 18–20 ГБ, хотя само приложение занимало ~130 МБ.
- **Причина:** macOS приписывает приложению всю его группу процессов (coalition). Приложение, запущенное из терминала агента, попадает в группу хост-процесса BB вместе со всеми агентами, тестами и браузерами (19,8 ГБ), и окно подписывает эту сумму именем единственного GUI-приложения в группе — Electron.
- **Решение:** запускать приложение через `open -n node_modules/electron/dist/Electron.app --args "$PWD"` — у него своя группа и свои цифры. Сторож памяти меряет только процессы приложения (`app.getAppMetrics` + footprint).

### [2026-10-21] Спам-шаблоны по кластеру и спам-чаты
- **Контекст:** спам-кампания «Нужно помочь/сделать пару/несколько карточек. Оплата по результату/сдельная» шла с десятка новых аккаунтов по разным чатам и прошла в лиды: SimHash не видит перестановку слов. Владелец попросил выходить из чатов, где только спам и повторы или нет новых сообщений, и больше в них не вступать.
- **Решение (шаблоны):** кроме SimHash — совпадение основ слов (первые 5 букв, Jaccard ≥ 0,3 при ≥ 8 основах): варианты кампании совпадают на 0,22–0,39 и связываются по цепочке, настоящие запросы против них ≤ 0,11. Кластеры, к которым подходит одно сообщение, сливаются; шаблон привязан к кластеру и ловит любой его вариант. При запуске старые лиды входят в кластеры, повторы одного автора сворачиваются в первый лид.
- **Решение (спам-чаты):** раз в 6 часов по каждому активному источнику берём последние 100 сообщений из Telegram. Живое — свой текст человека, не повтор (меньше 3 копий) и не кампания (меньше 3 авторов); посты от имени чата не живые. Спам-чат — от 20 текстов и живых меньше 20 %; мёртвый — нет нового текста неделю. Такой чат покидаем на всех аккаунтах, источники получают статус `spam`, `joinChat` и добавление источника отказывают, в поиске метка «спам-чат». Владелец отмечает чат вручную в «Чатах» и разблокирует в «Спаме». Каналы не оцениваются (у канала один автор — все посты «от имени чата»; так ошибочно ушли из канала владельца «Помогающий Маркетолог»), и чаты, где аккаунт — создатель или администратор, не покидаются никогда. История берётся с сервера (`only_local: false`) — оценивается то, что осталось после чистки ботами.
- **Почему по истории, а не по накопленным отпечаткам:** отпечатки набираются только из прошедших фильтр сообщений и неделями; история даёт решение сразу и честную дату последнего сообщения.

### [2026-10-21] Чат канала и «Новости»
- **Чат канала:** канал как источник — это его чат обсуждений (`linked_chat_id` из `getSupergroupFullInfo`): лиды пишут в комментариях, а вступить в чат можно без подписки на новости канала. `chats.discussion` отдаёт чат, `sources.add` с каналом добавляет его чат, в «Чатах» у канала кнопка «Вступить в чат канала».
- **Новости:** список каналов читается без подписки (публичная история) раз в час и по кнопке. Jev одним запросом на 10 постов оценивает «стоит ли репоста или обзора» против `settings.newsInterests`; от 50 % пост попадает в список с выжимкой и «чем полезно» от основной LLM. Черновик репоста или обзора — по кнопке, той же LLM. Первое чтение — только последние трое суток; посты короче 80 символов не оцениваются.
- **Почему Jev, а не LLM на каждый пост:** оценка дешёвая и пакетная, LLM тратится только на прошедшие порог.

### [2026-10-21] Ссылки Telegram открываются внутри приложения
- **Решение:** любая ссылка `t.me` / `telegram.me` / `tg://` — кнопки новостей и статистики, ссылки в текстах сообщений и постов, `window.open`, переход окна — уходит событием `link:open` в интерфейс; `chats.resolveLink` (TDLib `getMessageLinkInfo`, без вступления) даёт чат и сообщение, «Чаты» открываются на нём с подсветкой. Кнопки «Открыть в Telegram» убраны, у сообщения — «Скопировать ссылку».

### [2026-10-21] Допродажа и уроки умений
- **Допродажа:** агент отвечает за средний чек. После того как у лида появился заказ, в промпт оператора добавляется блок `<upsell>`: 1–2 услуги из каталога с вилкой цены и причиной. Источники — естественные пары услуг (`src/main/agent/upsell.ts`: к контент-плану обложки и тексты постов, к карточке инфографика и карточки остальных товаров…) и то, что другие клиенты реально заказывали следом. Предлагать — одно за раз, после согласия на цену или довольного «готово», как выгоду; перед этим инструмент `offer_addon` записывает предложение, и та же услуга не предлагается лиду 30 дней. Во встроенных умениях раздел «Что предложить дальше»; выученные черновики умений тоже его получают.
- **Уроки умений:** умение, которое агент загрузил для лида, учится на завершённом заказе: вспомогательная модель по брифу, результату, числу правок и переписке пишет 0–2 урока-правила (без деталей клиента), повторы отбрасываются, хранится до 12 последних. Уроки приклеиваются к умению при загрузке («Уроки из прошлых заказов»), видны и удаляются на странице «Умения». Новые умения из повторяющихся заказов по-прежнему черновиком на утверждение.
- **Почему уроки без утверждения:** это короткие уточнения к утверждённой инструкции, их видно и можно удалить; новое умение меняет поведение сильнее и остаётся на утверждении.

### [2026-10-21] «Свои люди», ответы после перезапуска, Markdown в Telegram
- **Свои люди** (`src/main/trusted.ts`, «Настройки → Свои люди»): задания бесплатно — так владелец тренирует агента на реальных задачах. Личное сообщение такого контакта без лида открывает лид личного чата; агент отвечает им даже при выключенном ИИ-менеджере и без лимита ответов; в промпте блок `<free_client>` вместо допродажи (цен и счетов нет); `request_payment` сразу ставит заказ в работу за 0 ₽, `run_task` не тратит квоту подписки. По желанию — ежедневное касание: после заданного часа, если сегодня ещё не общались, агент сам пишет (ход с системной заметкой, текст пишет модель с учётом прошлых задач), отправка через лимитер аккаунта. Список хранится в базе, не в коде (репозиторий публичный).
- **Ответ не теряется при перезапуске:** при запуске диалоги, где последнее сообщение входящее и не старше 2 часов, снова ставятся в очередь менеджера (он сам проверяет, включён ли он для лида).
- **Markdown → сущности Telegram:** ответы модели с `**жирным**`, `` `кодом` ``, `[ссылками](…)` и заголовками отправляются форматированием, а не звёздочками (`src/main/telegram/markdown.ts`).

### [2026-10-21] Rich Messages от агента — только с Telegram Premium
- **Решение:** ответ агента со структурой (заголовки, списки, таблицы, цитаты, жирный, ссылки) отправляется Rich Message из блоков (`richMessageSourceBlocks`, Markdown → блоки в `src/main/telegram/markdown.ts`; Markdown/HTML-исходник TDLib разрешает только ботам). Короткий обычный текст — обычным сообщением. Входящие и свои Rich Messages читаются в текст для истории и агента.

Движок проверяет Premium аккаунта (`getMe.is_premium`, раз в час) и без него сразу шлёт обычное сообщение с форматированием (жирный, код, ссылки — сущностями, не звёздочками). После покупки Premium Rich Messages включатся сами в течение часа.

### [2026-10-21] Карточки маркетплейсов: зрение, пример оформления, Muse Image 3:4
- **Контекст:** владелец прислал фото своей кровати и пример чужой карточки; агент ответил текстом с «[уточнить у продавца]» и 3 горизонтальными слайдами без текста, второй слайд с другим изголовьем.

Исполнитель одним проходом со зрением делит фото на товар и пример, пишет текст без заглушек (неизвестное — в «пришлите»), слайды — сколько просит клиент (по умолчанию 3, до 8), у каждого русский заголовок и подписи; генерация — Muse Image (`meta/muse-image/edit`, fal.ai) в 3:4 с фото товара и примером оформления; запрещены выдуманные размеры, материалы и комплектация. Для своих людей агент сначала сам уточняет детали одним списком, затем `start_work` запускает заказ без оплаты.

### [2026-10-21] Текст и картинки одним сообщением; заказы переживают перезапуск

Один проход лимитера, одна запись в истории («[вложения: 5 фото]»).

Дневной лимит — на холодные первые сообщения и рассылки.

- **Асинхронно:** инструмент `assign_task` ставит поручение subagent-у в очередь (`src/main/agent/tasks.ts`, таблица `agent_tasks`) и сразу возвращает управление — агент отвечает клиенту и продолжает разговор. ### [2026-10-21] Почему агент замолчал: пустой спам-шаблон, передача себе, квота поиска
- **Причины:** (1) спам-шаблон собрался из сообщений-упоминаний («@bot @user»), после нормализации — пустая строка, и он скрыл все лиды с пустым текстом публикации, т.е. личные диалоги своих людей; (2) агент передал диалог владельцу (`handoff`), а со своими людьми владелец и есть заказчик — диалог заперся; (3) у Tavily кончилась квота (HTTP 432); (4) решатель без зрения не видел формул на фото; (5) к заказу на домашку прикрепились фото кроватей из прошлого заказа; (6) исполнитель однажды повис без ответа модели.
- **Решение:** тексты короче 5 символов после нормализации не участвуют в спам-кластерах и шаблонах; для своих людей `handoff` только уведомляет владельца; `web_search` при сбое Tavily ищет через Google (Gemini grounding, ключ `geminiApiKey`); решатель на Gemini со зрением; к новому заказу прикрепляются только фото после предыдущего заказа; запуск исполнителя ограничен 10 минутами.

### [2026-10-21] Все модели — через собственный OpenCode v2 приложения
- **Контекст:** владелец: всё общение с моделями нативно через OpenCode v2, никаких прямых обращений к API провайдеров; выбор основной и вспомогательных моделей, автоматический подбор модели и уровня рассуждения; приложение само ставит и обновляет OpenCode.
- **Решение:** `src/main/opencode/`: `runtime.ts` скачивает `@opencode/cli-<платформа>` из реестра npm в userData, проверяет sha512 и запуск, хранит прежнюю версию для отката, проверка обновлений раз в сутки; `server.ts` запускает `opencode serve` на 127.0.0.1 со своими HOME/XDG, паролем (`OPENCODE_SERVER_PASSWORD`), конфигом (`OPENCODE_CONFIG_DIR`), без проектных конфигов и навыков Claude; `config.ts` пишет провайдеров (ключи — файлами 0600), наших агентов (запрет всего, кроме своих инструментов приложения) и плагин-мост; `bridge.ts` — HTTP на 127.0.0.1 с токеном: плагин получает список инструментов (`tgs_*`, `codemode: false`) и пересылает вызовы с `sessionID`, приложение по сессии знает диалог, проверяет разрешения и согласования владельца, выполняет инструмент, пишет трассу. Ход оператора — постоянная сессия диалога (`opencode_sessions`, в запрос — свежий контекст и новые сообщения), субагенты и фоновые поручения — свои сессии с фото во вложениях; всё остальное (исполнители заказов, сжатие диалогов, подписи, досье, уроки, новости) — через шлюз `ai/gateway.ts` одноразовыми сессиями. Пока движок не готов, запросы к моделям завершаются ошибкой с причиной — тихого отката на прямой API нет. Маршрутизация (`models.ts`): роли chat/fast/vision/smart, нужны ли инструменты и зрение, уровень рассуждения по роли (variant).
- **Не через OpenCode:** генерация картинок (fal.ai), распознавание и синтез речи, оценки Jev, локальные эмбеддинги памяти и поиск в сети инструментом приложения — это не модели-собеседники.
- **Системный OpenCode владельца:** v2 поставлен рядом (`opencode2`), `opencode` по-прежнему v1 для lane-stack; приложение использует только свою копию.

### [2026-10-21] Навык Rich-сообщений: обучающие решения со сворачиваемыми пояснениями
- **Контекст:** решение задачи уходило клиенту голым текстом; владелец хочет обучающий формат, где пояснения «почему так и по какому правилу» скрыты в сворачиваемых блоках.
- **Решение:** `RICH_FORMAT` в `agent/style.ts` — когда оформлять (решения, результаты поручений, расчёты, сравнения, цены, инструкции) и как; входит в системный промпт каждого агента OpenCode, потому что результаты субагентов уходят клиенту как есть. Решение задачи строится так: условие цитатой, шаги, под каждым свёрнутое «Почему так», **Ответ**, свёрнутые «Проверка» и «Где обычно ошибаются». Конвертер `markdownToBlocks` понимает `<details><summary>` (→ `inputPageBlockDetails`, `<details open>` — раскрыт), формулы LaTeX `$…$` и `$$…$$` (→ math-блоки) и `||спойлер||`; без Premium тот же текст уходит обычным: заголовок свёрнутого блока жирной строкой, формулы — моноширинным шрифтом. Исполнитель домашки просит у модели тот же формат.

### [2026-10-21] Бесплатные модели OpenRouter первыми; результат поручения проверяет основной агент
- **Контекст:** владелец: задействовать бесплатные модели OpenRouter, чтобы роутер сам отдавал им работу, а основной агент (GLM) фиксировал задачу, получал результат обратно и отправлял клиенту.
- **Решение:** бесплатные — `openrouter/*:free` и `openrouter/free` (нулевая цена у `openrouter/auto`, `fusion` и т. п. — не бесплатность, они списывают цену выбранной модели). Настройка `aiUseFree` (по умолчанию вкл.): они участвуют без отметок. `rankModels` строит очередь попыток: для поручений и вспомогательной работы сначала 2–3 подходящие бесплатные (сложные — крупные с рассуждением, простые — быстрые, с картинками — со зрением; крошечные и модерационные не берутся), затем отмеченные платные по прежнему правилу. Переписку с клиентом ведёт основная модель. Сбой модели (ошибка, лимит 429, пустой результат у субагента) — попытка уходит следующей модели в той же сессии, сбойная отдыхает 10 минут, при лимите — 30; ход основного агента повторяется, только если клиент ещё ничего не получил.
- **Поручения:** готовый результат больше не уходит клиенту сам — он приходит основному агенту системным сообщением; тот проверяет и отправляет его как есть через `send_task_result` (своё короткое вступление, текст и файлы не переписываются) или один раз бесплатно перепоручает с `redo_of`. Если агент не взялся (автоответы выключены, диалог у владельца, модель упала) — результат уходит клиенту напрямую, как раньше. Заодно исправлено: фото клиента снова прикладываются к поручениям аналитику и решателю (после перехода на роли проверка `model === 'gemini'` перестала срабатывать).
- **Риски:** у бесплатных моделей OpenRouter дневной лимит запросов и часть из них сохраняет запросы для обучения — для конфиденциальной переписки переключатель выключается.

### [2026-10-21] Подбор бесплатной модели по её описанию и нуждам агента
- **Контекст:** владелец: `openrouter/free` («Free Models Router») — не модель, а маршрутизатор OpenRouter, куда он уведёт запрос, мы не видим; задания распределять по тому, для чего модели предназначены по описанию.
- **Решение:** маршрутизаторы OpenRouter (`openrouter/free`, `auto`, `fusion`…) не используются; бесплатные — только `*:free`. У агента в файле поле `needs` (логика, код, тексты, русский, картинки, инструменты, длинные документы и факты, скорость; редактируется в «Агентах»): решатель — логика; копирайтер — тексты и русский; исследователь — длинные документы, инструменты, русский; аналитик — картинки и логика; директолог — тексты, русский, логика. Раз в сутки (и при запуске) приложение берёт из публичного каталога `openrouter.ai/api/v1/models` (без ключа, модели не вызываются) описания, модальности, параметры и дату отключения бесплатных и отмеченных моделей OpenRouter; основная модель ставит по описанию оценки 0–3 по навыкам и пишет строку «для чего лучше всего» (`model_profiles`, переоценка — только при смене описания). Маршрутизатор берёт бесплатные модели в порядке суммы оценок по нуждам агента; модель с нулём по нужному навыку и снятая с бесплатного доступа не берётся; без профиля — прежняя оценка по имени. В настройках у моделей видны описание и сильные стороны.

### [2026-10-21] Подписки наравне с бесплатными; модель под задачу выбирает Jev по английским описаниям
- **Контекст:** владелец: модели по подписке (Z.ai, OpenLux, 9router) можно использовать свободно, наравне с бесплатными; русское описание — только для показа, выбирать модель должен Jev по английскому описанию.
- **Решение:** подписочная модель — не из OpenRouter и без цены за токены; отмеченные галочкой (и основная) такие модели — в «первой линии» вместе с бесплатными OpenRouter (их — по переключателю); неотмеченные работу не получают — галочка и есть разрешение. Подписочная модель берёт описание той же модели на OpenRouter (сопоставление по названию и версии: «Gemini 3.8 Flash (High)» → `google/gemini-3.8-flash`, «claude-opus-5-5» → `anthropic/claude-opus-5.5`); не нашлось — Jev судит по названию и параметрам. В профиле хранится исходное английское описание (`about`); оценки и русская строка от основной модели — для настроек и как запасной порядок. Jev недоступен — порядок по профилям. В настройках блок «Кому достанется задача» показывает этот выбор на примере.

### [2026-10-21] Агент замолчал: пауза при доставке результата и провал дублирующего заказа
- **Причины:** (1) результат поручения пришёл, пока шла пауза между отправками после «взял задачу» — прямая доставка упала на «Пауза между отправками», готовое поручение стало «проваленным», а провал перевёл диалог на владельца; (2) на «а 15 реши» агент запустил и поручение аналитику, и заказ исполнителю домашки; исполнитель не нашёл фото (к заказу прикрепляются только фото после прошлого заказа, а страница пришла раньше), его провал снова перевёл диалог на владельца, и ход агента с проверкой результата не состоялся.
- **Решение:** доставка результата (инструмент `send_task_result` и запасной путь) ждёт конца паузы (`waitForSendWindow`, до 10 минут); ошибка доставки не превращает готовое поручение в проваленное — ещё одна попытка через 2 минуты, о второй неудаче сообщается; провал поручения или заказа у «своих людей» не отключает агента; заказ той же услуги без новых фото берёт входные файлы прошлого заказа; агенту — правило «одна просьба — один путь» (заказ через `start_work` или `assign_task`, не оба); возврат диалога агенту (`setHandoff(false)`) сразу запускает ответ на сообщения без ответа. Консоль основного процесса пишется в `userData/logs/main.log` (ротация 5 МБ) — раньше такие сбои было не разобрать.

### [2026-10-21] После перезапуска агент отвечает на ждущие сообщения
- **Контекст:** ответ клиенту планируется в памяти (пауза перед ответом, ход агента); перезапуск приложения в этот момент оставлял сообщение без ответа. Поручения и заказы в работе и так продолжаются (очередь в базе).

### [2026-10-21] Журнал моделей, проверяющая модель и маршрутизация с учётом истории
- **Журнал (`model_runs`):** каждая попытка вспомогательной работы — поручения субагенту, запросы исполнителей заказов (контекст `withJob` через `AsyncLocalStorage` — запросы заказа записываются под его видом и номером), служебные запросы: модель, вид работы, задача, исход (готово / сбой / пусто / таймаут / отклонено проверяющим), оценка и замечание проверяющего, отметка основного агента (принял через `send_task_result`, вернул через `redo_of`), правки клиента по заказу, время, стоимость. Переписка с клиентом основной моделью в журнал не идёт.
- **Проверяющая модель:** у агента `verify` (`always` / `free` / `off`; по умолчанию субагенты — `free`, т. е. проверяется работа бесплатных моделей) и `check` — свой список проверок поверх общего (отвечает на поручение, без выдумок, без противоречий, язык). Проверяющий — настройка `aiVerifierModel`, иначе отмеченная Gemini 3.8 Flash High, иначе самая сильная отмеченная подписочная; никогда не та же модель; со зрением, если есть картинки. Оценка ниже 0.7 — задача уходит следующей модели в той же сессии с замечаниями; все отклонены — отдаётся лучший по оценке (основной агент всё равно проверяет).
- **Маршрутизация:** порядок первой линии = соответствие задаче от Jev × надёжность модели на этом виде работы за 30 дней ((удачные + 1) / (все + 2); без истории — 0.5, нейтрально, чтобы новая модель получала шанс).
- **Статистика:** раздел «Модели в работе» — по модели и виду работы: задач, принято, отклонил проверяющий, переделки, правки клиента, сбои, средняя оценка, время.
